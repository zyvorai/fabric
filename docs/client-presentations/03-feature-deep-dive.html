Cloud-Init Integration

Automated VM provisioning with NoCloud datasource

What cloud-init Provides

  • Automatic hostname configuration
  • SSH key injection for passwordless access
  • User and group creation
  • Package installation on first boot
  • Custom script execution
  • Network configuration
  • Disk partition and filesystem setup

How It Works

  1. User provides cloud-init config via API or CLI
  2. Zyvor Fabric generates a NoCloud datasource ISO
  3. ISO is attached to the VM automatically
  4. VM boots and cloud-init runs on first start
  5. Configuration is applied, VM is ready to use

  - htop

  - systemctl enable --now docker

Live Migration

Move running VMs between hosts with minimal downtime

How It Works

  1. Pre-copy phase -- iterative rsync of VM disk to target host
  2. Memory transfer -- copy VM memory pages
  3. Convergence -- track dirty pages, re-copy changed regions
  4. Cutover -- brief pause, final sync, resume on target
  5. Cleanup -- remove source VM data

Storage Live Migration

  • Move VM disks between storage pools
  • Migrate from local to shared storage
  • No VM downtime during disk migration
  • Supports all 6 storage backends

Migration Triggers

  • Manual -- operator-initiated via CLI, API, or Web UI
  • DRS -- automatic load balancing across cluster
  • Maintenance -- evacuate host for planned downtime
  • Failover -- automatic migration on host failure

Placement Controls

  • Affinity rules -- keep VMs together
  • Anti-affinity rules -- separate VMs across hosts
  • Host constraints -- restrict VMs to specific nodes
  • Resource requirements -- CPU, memory, GPU matching

2FA / MFA Authentication

TOTP-based two-factor authentication for every user account

How It Works

  1. User calls POST /api/auth/2fa/setup to generate a TOTP secret
  2. Server returns the secret and an otpauth:// URL for QR scanning
  3. User scans the QR code with Google Authenticator, Authy, or any TOTP app
  4. User confirms setup by verifying a code via POST /api/auth/2fa/verify
  5. All subsequent logins require a 6-digit TOTP code in the totp_code field

Security Benefits

  • Protects against stolen passwords
  • Per-user enable/disable -- no global toggle
  • TOTP secrets stored encrypted in the user database
  • Constant-time code verification prevents timing attacks

API Flow

# Step 1: Set up 2FA
POST /api/auth/2fa/setup
Authorization: Bearer <token>

# Response:
{
  "secret": "BASE32SECRET...",
  "otpauth_url": "otpauth://totp/Zyvor Fabric:admin?..."
}

# Step 2: Verify setup
POST /api/auth/2fa/verify
{"code": "123456"}

# Step 3: Login with 2FA
POST /api/auth/login
{
  "username": "admin",
  "password": "...",
  "totp_code": "654321"
}

Secrets Management

Centralized secret storage with encryption at rest

Capabilities

  • Create, retrieve, and delete secrets via REST API
  • Values encrypted at rest -- never returned in list responses
  • Attach metadata (key/value pairs) to each secret
  • Admin-only access enforced by RBAC
  • Audit logged on every create, read, and delete

Injection into VMs

  • Secrets can be injected at boot via systemd credentials
  • Delivered through SMBIOS or VSOCK -- never on command line
  • Guest reads credentials with systemd-creds cat
  • Credential IDs validated (alphanumeric + dots/hyphens only)

API Examples

  -H "Authorization: Bearer $TOKEN" \

  -d '{

    "value": "s3cretP@ss!",
    "metadata": {"env": "production"}
  }'

# List secrets (values redacted)
curl "$HOST/api/secrets" \
  -H "Authorization: Bearer $TOKEN"

# Delete a secret

  -H "Authorization: Bearer $TOKEN"

USB Passthrough

Attach host USB devices directly to VMs

Use Cases

  • Hardware security keys (YubiKey, FIDO2)
  • USB storage devices
  • Serial adapters and specialized hardware
  • Printers and scanners
  • USB dongles for licensed software

How It Works

  1. List available USB devices on the host via GET /api/system/usb
  2. Identify the target device by vendor ID and product ID
  3. Pass the device to the VM at start time via QEMU USB passthrough
  4. Guest OS detects the device as a native USB peripheral

List Available Devices

# List host USB devices
curl "$HOST/api/system/usb" \
  -H "Authorization: Bearer $TOKEN"

# Response:
[
  {
    "bus": 1,
    "device": 4,
    "vendor_id": "1050",
    "product_id": "0407",
    "description": "Yubico YubiKey"
  }
]

Pass to VM at Start

curl -X POST "$HOST/api/vms/my-vm/start" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "kvm": true,
    "extra_args": [
      "usb_host=1050:0407"
    ]
  }'

Rust SDK

Type-safe client library for programmatic API access

Features

  • Automatic authentication and token management
  • Type-safe request and response structs
  • Covers the full 520+ endpoint API surface
  • Built-in retry and error handling

When to Use

  • Custom automation tools

  • Building higher-level orchestration layers
  • Testing and validation scripts

Quick Start

# Cargo.toml
[dependencies]
vmspawn-sdk = "0.1"
tokio = { version = "1", features = ["full"] }
use vmspawn_sdk::{Client, ClientConfig};

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let client = Client::new(ClientConfig {
        base_url: "https://host:3000".into(),
        token: Some("your-jwt-token".into()),
        ..Default::default()
    })?;

    // List VMs
    let vms = client.list_vms().await?;
    for vm in vms {
        println!("{}: {}", vm.name, vm.status);
    }

    Ok(())
}
