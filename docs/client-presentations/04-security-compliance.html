Authentication

PAM + JWT with enterprise SSO integration

Authentication Methods

PAM (Primary)

Authenticate against system users via Pluggable Authentication Modules. Supports local accounts, LDAP backends, and any PAM-compatible identity provider.

JWT Tokens

After PAM authentication, users receive a JWT token for subsequent API calls. Configurable expiration. Token revocation and blacklisting supported.

API Keys

Long-lived tokens for service-to-service authentication. Scoped permissions. Separate rate limiting. Audit logged.

Enterprise SSO

Connect to Active Directory or OpenLDAP. Map LDAP groups to vmspawn roles. Automatic user provisioning on first login.

OIDC / OAuth2

OpenID Connect for modern SSO. Compatible with Okta, Auth0, Keycloak, Azure AD, and Google Workspace.

2FA / TOTP Authentication

Time-based one-time passwords for every user account

How It Works

  1. User calls POST /api/auth/2fa/setup to generate a TOTP secret
  2. Server returns the secret and an otpauth:// URL
  3. User scans the QR code with an authenticator app
  4. User confirms by verifying a code via POST /api/auth/2fa/verify
  5. Subsequent logins require the totp_code field

Security Properties

  • TOTP secrets encrypted at rest in the user database
  • Constant-time code verification (no timing side channel)
  • Per-user enable/disable -- not a global setting
  • Missing code returns 401 with requires_2fa: true
  • Invalid code returns 401 and is rate-limited

JWT Token Revocation

Invalidate compromised tokens instantly

Token Lifecycle

  • JWT tokens issued on successful login (PAM + optional 2FA)
  • Configurable expiration time
  • Token blacklist checked on every authenticated request
  • Revoked tokens rejected immediately at the middleware layer
  • Blacklist entries cleaned up after token expiry

When to Revoke

  • User account compromised
  • Employee offboarding
  • Suspicious activity detected in audit logs
  • Password or role change

Example: VM Name Validation

// Rejects: "../escape", "rm -rf", ""
// Accepts: "web-01", "db-primary", "test123"
fn validate_vm_name(name: &str) -> Result<()> {
    if name.is_empty() || name.len() > 64 {
        return Err(ValidationError::Length);
    }
    if !name.chars().all(|c|
        c.is_alphanumeric() || c == '-' || c == '_'
    ) {
        return Err(ValidationError::InvalidChars);
    }
    Ok(())
}

Command Injection Prevention

Zero shell pipelines -- all subprocess calls use safe argument passing

The Threat

Command injection is one of the most critical web application vulnerabilities. If user input reaches a shell, attackers can execute arbitrary commands on the host.

Unsafe Pattern (Never Used)

// DANGEROUS: shell injection possible
let output = Command::new("sh")
    .arg("-c")
    .arg(format!("qemu-img info {}", user_input))
    .output();

If user_input is "img.qcow2; rm -rf /", the shell executes both commands.

Safe Pattern (Always Used)

// SAFE: arguments passed directly, no shell
let output = Command::new("qemu-img")
    .arg("info")
    .arg("--output=json")
    .arg(&validated_path)
    .output();

Arguments are passed as an array. No shell interpretation. Special characters are treated as literal strings.

Enforced Practices

  • All subprocess calls use Command::new() with .arg()
  • No sh -c or bash -c invocations
  • No string interpolation into commands
  • Validated and sanitized inputs only
  • Audited across all 40+ crates

Path Traversal and SSRF Prevention

Protecting against file system and network attacks

Path Traversal Protection

Attackers attempt to access files outside intended directories using sequences like ../../etc/passwd.

Defense Mechanism

  • All file paths are canonicalized before use
  • Resulting path must be within allowed directories
  • Symbolic links are resolved and checked
  • Null bytes in paths are rejected
// Canonicalize and verify containment
let canonical = path.canonicalize()?;
if !canonical.starts_with(&allowed_base) {
    return Err(SecurityError::PathTraversal);
}

SSRF Prevention

Server-Side Request Forgery (SSRF) tricks the server into making requests to internal services or metadata endpoints.

Defense Mechanism

  • User-provided URLs are validated before use
  • Private IP ranges are blocked (10.x, 172.16.x, 192.168.x)
  • Loopback addresses blocked (127.0.0.1, ::1)
  • Cloud metadata endpoints blocked (169.254.169.254)
  • Only HTTP/HTTPS schemes permitted
  • DNS resolution checked against blocked ranges

Applied to: cloud image downloads, webhook URLs, ISO downloads, and any user-specified URL.

Rate Limiting

Brute force protection and abuse prevention

Authentication Rate Limiting

Login Endpoint

  • 5 attempts per 5 minutes per source IP
  • Failed attempts logged with source details
  • Lockout response with retry-after header
  • Prevents credential stuffing and brute force

API Key Endpoints

  • Separate rate limits for key validation
  • Invalid key attempts tracked
  • Automatic lockout on excessive failures

Why Rate Limiting Matters

Without rate limiting, an attacker can attempt thousands of passwords per second. With vmspawn's limits:

ScenarioWithout LimitingWith Limiting
Attempts/hour360,000+60
4-digit PIN brute force~1 second~28 hours
6-char password~5 minutes~19 years

Additional Protections

  • bcrypt cost factor 12 adds ~250ms per attempt
  • Constant-time comparison prevents timing attacks
  • No user enumeration (same response for valid/invalid)
